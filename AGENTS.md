# AGENTS.md — City Council Minutes

A handbook for anyone (human or agent) extending this pipeline. Read this before
touching code.

## What this project does

Liberates every signed set of Boulder City Council minutes, 2000–present, from the
city's Laserfiche WebLink portal (`\Central Records\City Council\Signed Minutes`,
folder id 10888) into linked tables of meetings, attendance, agenda items,
speakers, motions, and per-member votes.

```
Laserfiche ──discover──▶ inventory.csv ──sample/fetch──▶ PDFs (LFS) + manifest.csv
   ──Datalab /convert──▶ markdown (OCR) ──Datalab /extract──▶ extraction JSON
   ──tidy──▶ data/processed/*.csv + meetings.json ──score/audit──▶ data/audit/*.md
```

Each stage is idempotent and resumable; run them with `uv run python -m scripts <stage>`.

## Layout

| Path | What | Mutable? |
|---|---|---|
| `data/original/laserfiche/listings/<folderId>.json` | raw folder listings from the portal | re-listed only with `discover --refresh` |
| `data/original/laserfiche/inventory.csv` | one row per document found | regenerated by `discover` |
| `data/original/laserfiche/pdf/<year>/<entry_id>.pdf` | the minutes (Git LFS) | **immutable** |
| `data/original/laserfiche/manifest.csv` | hash, bytes, method, page count per PDF | append-only |
| `data/interim/datalab/markdown/<year>/<entry_id>.md` | Datalab OCR output | regenerate only on purpose |
| `data/interim/datalab/extract/<mode>/<year>/<entry_id>.json` | Datalab extraction, with citations + verification | keyed by schema version |
| `data/interim/datalab/runs.csv` | every Datalab job: pages, cost | append-only |
| `data/processed/` | the dataset (tables, nested JSON, provenance) | regenerated by `tidy` |
| `data/interim/tidy/<mode>/` | per-mode tables rebuilt by `score` (gitignored) | regenerated |
| `data/lookups/` | sample definition, hand-transcribed reference, member aliases, `adjudications.csv` (disagreements checked against the minutes) | hand-maintained |
| `data/audit/` | `accuracy.md`, `summary.md`, cost projection; `sample_report.md` is hand-written | regenerated (except `sample_report.md`) |
| `docs/aar/` | after-action reports, `AAR_<repo>_<date>.md`; the next AAR checks their tracking tables | append |
| `certs/boulder-ca-bundle.pem` | CA bundle for the city's server | rebuild with `certs/make_ca_bundle.py` |

## Gotchas (learned the hard way)

1. **TLS.** `documents.bouldercolorado.gov` omits its intermediate certificate. All
   requests verify against `certs/boulder-ca-bundle.pem` (from the CU Info Science
   *Web Data Science Book*, ch. 9). Never use `verify=False`.
2. **Rate limit.** The portal stops answering after ~15 requests in a burst and
   recovers after ~5 minutes. `LaserficheClient` pauses every 12 requests and backs
   off 5.5 min on any failure. A full crawl therefore takes hours; run it in the
   background and let it resume from the listing cache.
3. **Two kinds of record.** Pre-2013 minutes are *imaged* (scanned pages, no file).
   `ElectronicFile.aspx` returns an empty 200 for them; use the viewer's
   `GeneratePDF10.aspx` → `DocumentService.aspx/PDFTransition` → `PDF10/<key>/<id>`
   flow, which needs the session cookie `DocView.aspx` sets. Rendered PDFs get new
   bytes every time, so their SHA-256 is not stable — compare page counts.
   Faster: the browse page's bulk export (`ZipEntriesHandler.aspx/StartExport`) returns
   one ZIP with a PDF per entry, ~6–10 requests per 25 records. `fetch` uses it by
   default and falls back to per-entry downloads. The export job is bound to the
   session that started it. On any portal, check the browse/search page's own
   batch features before building a per-record fetcher; requests per record is the
   number that decides throughput under the rate limit.
   Don't probe the portal while a crawl or fetch is running: both share the same
   ~15-request budget and the probe triggers a five-minute block for both.
4. **Folder layout changes.** Early years list minutes directly under the year;
   later years nest month folders (`01 JAN`, `09 SEPT`). `discover` walks recursively.
5. **Names carry the date, inconsistently.** `Minutes - Apr-01-2003`,
   `City Council Minutes - 2018-12-04`, `... - 12.01.20`. `parse_name_date` handles
   these; the extracted `meeting_date` wins when present and disagreements are flagged.
6. **Datalab checkpoints expire.** `extract` reuses the `/convert` checkpoint to avoid
   paying for OCR twice; if it has expired, it re-sends the PDF (and pays to re-parse).
7. **Balanced vs. fast extraction.** Measured on the sample: balanced ≈ $31 per 1K
   pages, fast ≈ $5, OCR ≈ $3. Balanced finds ~10% more motions (25% more in 2005–09),
   and its counts match the vote sentences in the text; fast both misses and invents
   motions. Use balanced — see `data/audit/sample_report.md`.
8. **The hand-transcribed reference has errors** (e.g. the 2022-09-14 record lists the
   2021 council). Treat `accuracy.md` disagreements as things to adjudicate.
9. **Vote inference is deterministic and flagged.** The extractor records only stated
   votes; `tidy.infer_votes` fills in the rest from the meeting's roll call and marks
   those rows `vote_source = inferred`. It declines when counts don't reconcile,
   unless the attendance notes ("arrived at 6:45 p.m.", "left at 9:30 p.m.", a
   "Yates - Late" roll-call marker) account for exactly the difference; those rows get
   `inference_basis = attendance_note` (otherwise `roll_call`). A noted member seen
   moving, seconding, or voting by name around that motion doesn't count as away.
   Recusals or nays on one consent item beside a whole-agenda tally ("Carried 9:0;
   NAY: Nagle on Item F") go to `motions.item_level_exceptions`.
10. **Long runs and the working tree.** Fetch and Datalab runs take hours and write
    partial output continuously. If a commit-on-stop hook or watcher is active, run them
    against a copy of `data/` outside the repo and commit once at the end:
    ```bash
    mkdir -p /tmp/ccm && cp -r data /tmp/ccm/
    CCM_DATA_DIR=/tmp/ccm/data uv run python -m scripts fetch --scope all
    # … convert / extract …
    cp -r /tmp/ccm/data/. data/ && git add data && git commit
    ```
11. **Paid extraction has a spend limit.** The Datalab key has a 30-day billing limit;
    at the limit the API returns HTTP 402 and `datalab.py` stops the run cleanly. Before
    a batch, compare the projected cost (`data/audit/summary.md`) with the limit.
    Extraction always runs the hand-transcribed reference meetings first, so accuracy
    can still be scored if the limit is reached part-way.
12. **Contract vs. plausibility.** `scripts/schema.py` rejects only impossible values.
    Unusual-but-real ones (ten members at a post-election transition meeting) are
    flagged in `data/audit/summary.md` for review instead of failing the build.

13. **Not everyone on an extracted roll call is on council.** The extractor has listed
    public-hearing speakers marked "DID NOT SHOW" (2022-04-05), the absentees of a
    Planning Board vote quoted in a call-up (2008-07-08), and Planning Board members at a
    joint meeting (fast mode, 2016-10-13). `tidy.non_members` drops names with no
    corroboration (a council/mayor title, acting in the meeting, or a roll call within
    3 years) and lists them in `excluded_roll_call.csv` and `data/audit/summary.md`.
    Because corroboration comes from other meetings, a partial run (e.g. `--entry-ids`)
    has less to go on; check that list after any run.

## Checks by change type

Run the cheapest check that can catch a mistake in what you changed, and say in the PR
which one you ran. Everything below `extract` rebuilds from the cache in seconds, so
there is no reason to skip it, and no reason to re-run a paid stage to test a tidy change.

| Change touches | Run | Time | Cost |
|---|---|---|---|
| docs, comments | `pytest` | ~3 s | free |
| `tidy.py`, `names.py`, `schema.py`, lookups | + `tidy --mode balanced`, `score`, `audit` (from cache) | ~30 s | free |
| `extraction_schema.py` (bumps `SCHEMA_VERSION`) | + `extract` on the reference meetings first | minutes | **paid**: ask first (gotcha 11) |
| `laserfiche.py`, `discover.py`, `fetch.py` | + a small `--scope sample` run | 5 min+ | portal rate limit (gotcha 2) |

Compare `data/audit/accuracy_*.csv` before and after any tidy change. An agreement score
that drops is a regression until the minutes say otherwise.

## How to…

- **Pick up newly filed minutes:** `discover --refresh` (or `--refresh --years 2026`),
  then `fetch --scope all`, `convert --scope all`, `extract --scope all`, `tidy`, `audit`.
- **Change what is extracted:** edit `scripts/extraction_schema.py`, bump
  `SCHEMA_VERSION`, update `scripts/tidy.py`, `scripts/schema.py`, and
  `docs/data-dictionary.md` together. Old extractions are re-run automatically because
  their schema version no longer matches.
- **Fix a member name:** add a row to `data/lookups/member_aliases.csv`
  (`alias` as printed → `member` canonical last name).
- **Re-score:** `score` rebuilds per-mode tables under `data/interim/tidy/<mode>/` and
  writes `data/audit/accuracy.md`.
- **Record a checked disagreement:** add a row to `data/lookups/adjudications.csv`
  (`verdict` = `reference_error`, `extraction_error`, `both_partial`, …); `score` reports
  them beside the raw agreement.
- **Run the full archive:** raise the Datalab limit to cover the projection, then
  `fetch --scope all`, `convert --scope all`, `extract --scope all --mode balanced`,
  `tidy`, `score`, `audit` — with `CCM_DATA_DIR` if a hook is watching the repo (gotcha 10).

## Conventions

- Originals are immutable; all cleaning happens downstream.
- Provenance is a sidecar (`data/processed/provenance.csv`) keyed on `entry_id`, not
  repeated on every row.
- Tables validate against pandera contracts in `scripts/schema.py` before writing.
- Size a fix before recommending it. When `sample_report.md`, an audit note or a PR proposes
  a fix, give the number of records it would touch, from a query against the current data.
  Spot-check five against the minutes before writing the rule into code or a brief. The
  report once said attendance notes "could recover many" uninferred votes; the fix recovered
  3 of 62, and the first rule was wrong on 3 of its first 6 motions.
- Check at the grain you publish. The tables are per member × motion, so `score` compares
  each motion's named yeas and nays with the reference, not only motion counts. A tidy
  change isn't done until `accuracy_*.csv` is no worse. A new table needs a scored or
  audited check at its own grain before it ships.
- `entry_id` is the join key everywhere and resolves to
  `https://documents.bouldercolorado.gov/WebLink/DocView.aspx?id=<entry_id>&dbid=0&repo=LF8PROD2`.
